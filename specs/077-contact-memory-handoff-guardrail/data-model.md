# Phase 1 Data Model: Contact Memory Handoff Pretext Guardrail

**No schema change (FR-008).** No new table, column, migration, or model. The two entities below are
conceptual; the only storage-visible change is the free-text value written into the existing
`notes.content` column for *new* rows.

## Entity: Memory Note

- **Backing store**: existing upstream `Note` model / `notes` table (`belongs_to :contact`,
  `belongs_to :account`, `belongs_to :user` optional). Unchanged.
- **Relevant field**: `content` (text). From this feature onward, notes generated by
  `Custom::Scout::ContactNotesService` are written with a leading date token.
- **Content format (new rows only)**: `"[DD/MM/YYYY] " + <summary text>`
  - `DD/MM/YYYY` = generation date in the conversation's effective timezone (Decision 5, research).
  - The date is part of `content`, so it renders verbatim through
    `LlmFormatter::ContactLlmFormatter#build_notes` (Scout prompt) and the dashboard contact Notes
    view (which shows its own independent "written X ago" timestamp alongside — accepted overlap,
    FR-005 / User Story 4 scenario 3).
- **Lifecycle**: created only at handoff when `scout.feature_memory?` (via
  `HandoffService#generate_contact_memory` → `ContactNotesService#generate_and_update_notes`).
  Accumulates across a contact's conversations; surfaced at the start of every subsequent
  conversation with that contact.
- **Validation rules**:
  - A note is persisted only when its generated summary is present (existing `note.present?` guard);
    the date prefix is added only to a present note (never a lone `[DD/MM/YYYY]`).
  - Pre-existing notes are **never** modified to add a date (FR-006, Decision 6). No retroactive
    backfill.
- **Interpretation invariant (prompt-enforced, not schema-enforced)**: every note represents a
  prior, already-concluded conversation — never a fact or request active in the current turn
  (FR-001). This is asserted to the model by the memory-interpretation warning, not by data.

## Entity: Handoff Decision

- **Nature**: a per-turn judgment by Scout's main model, not a persisted record. Expressed as a call
  (or non-call) to the `handover_to_human` tool
  (`custom/app/services/custom/scout/tools/handover_to_human.rb`).
- **Governing invariant (FR-002)**: the deciding transfer signal MUST originate in the *current*
  conversation's own messages. A memory note MAY inform tone/anticipation (FR-003) but can NEVER
  stand alone as the sufficient justification for a handoff.
- **Unchanged paths** (FR-004, FR-007): a genuine present-turn human request still triggers immediate
  handoff via the same `handover_to_human` tool path; the Phase 12 `ResponseAuditor` /
  `ActionClassifierService` reactive safety net is unmodified.

## State transitions

None. No entity gains a new state, status column, or lifecycle stage. The feature only changes (a)
the text content written to new `Note` rows and (b) the instruction text Scout reads when a contact
already has notes.
