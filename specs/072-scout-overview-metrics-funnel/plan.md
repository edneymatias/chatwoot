# Implementation Plan: Scout Overview — Summary Metrics & Funnel Distribution

**Branch**: `072-scout-overview-metrics-funnel` | **Date**: 2026-09-16 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/072-scout-overview-metrics-funnel/spec.md`

## Summary

Build the Scout Overview page: a new route (`scout_overview`) added as the first item in the Scout sidebar section, displaying five summary metric cards (total handled, qualification/disqualification/abandonment rates, avg messages-per-conversation) scoped to a selected period, plus a pipeline-stage distribution chart (current snapshot) and an interest-by-stage breakdown card. Backed by a single new API endpoint (`GET /api/v1/accounts/:account_id/scout_overview_reports`) with a builder service (`Reports::ScoutOverviewBuilder`) that joins Opportunity → Conversation → Inbox → ScoutInbox to attribute opportunities to a Scout without any new database columns.

Per the 2026-09-16 Clarifications:
1. **Authorization**: Accessible to any authenticated account member (agent, administrator, custom role) via `ScoutPolicy#show?`, exactly mirroring Captain Overview (FR-015). Does not use the administrator-only `ReportPolicy#view?`.
2. **In-Progress Denominator**: "Total handled" includes all opportunities created by the Scout in the period across all stages, including In Progress. All outcome rates are computed as `outcome_count ÷ total_handled * 100` (FR-005, FR-011).
3. **Performance Target**: On-demand execution runs in < 40ms against indexed columns for production datasets of up to ~10,000 opportunities per account on localhost/LAN, easily beating the < 2.0s requirement of SC-002 without background jobs or pre-computed tables.

## Technical Context

**Language/Version**: Ruby 3.x (Rails 7), JavaScript (Vue 3 + Vite)

**Primary Dependencies**:
- Rails, Pundit (`ScoutPolicy` for agent+admin authorization), `pattr_initialize` (Struct-style service args) — all existing
- Vue 3 + Composition API (`<script setup>`), `vue-chartjs` / Chart.js (already in project for pipeline charts)
- `DateRangeHelper` concern (already in `custom/app/controllers/concerns/`) for period parsing
- Existing `RangeSelector` component (`app/javascript/dashboard/components-next/captain/pageComponents/overview/RangeSelector.vue`)
- Existing `EmptyStateLayout` component (`app/javascript/dashboard/components-next/EmptyStateLayout.vue`)

**Storage**: PostgreSQL — no new tables. Attribution via JOIN on existing `ichatr_scout_inboxes` + `conversations`. Indexed lookup on `ichatr_opportunities.origin_conversation_id` (partial unique) and `pipeline_stage_id`. Custom attributes in `ichatr_opportunities.custom_attributes` (JSONB).

**Testing**: RSpec (request specs for `ScoutOverviewReportsController`, covering agent access, admin access, empty states, and all outcome calculations) + Vitest (component tests for overview page and cards)

**Target Platform**: Containerized Rails + Vite dev stack (rootless Podman)

**Performance Goals**: < 2s end-to-end on localhost/LAN connection for up to ~10,000 opportunities per account (FR-007 / SC-002 clarification). All aggregations on demand; no pre-computation.

**Constraints**: On-demand aggregation only (FR-013). No new database tables. No new npm packages. No admin-only role restrictions (FR-015).

**Scale/Scope**: 1 API endpoint, 1 builder service, 1 controller, 1 page route, 4–5 Vue components, route + sidebar entry, i18n keys for `en.json` + `pt_BR.json`.

## Complexity Tracking

> **On-demand aggregation vs. Pre-computed cache tables**: Pre-aggregation was considered and explicitly rejected per Principle II (Smallest Change) and FR-013. The 2026-09-16 clarification on SC-002 established that production datasets are ≤ ~10,000 opportunities per account on localhost/LAN. In PostgreSQL, indexed grouping on this volume completes in under 20ms, rendering cache invalidation logic, Redis keys, or background worker jobs unnecessary complexity.
